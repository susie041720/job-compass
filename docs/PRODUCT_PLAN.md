# 产品与开发规划

## 用户与目标

主要用户是希望系统管理个人求职信息、但不熟悉编程的学生或求职者。核心任务是快速记录岗位、知道下一步要做什么，并在面试前找回完整资料。

## 页面结构

| 页面 | 首要任务 | MVP 内容 |
| --- | --- | --- |
| 数据概览 | 快速判断求职进展 | 核心指标、最近更新、阶段分布、下一步建议 |
| 投递记录 | 管理和查找申请 | 搜索、筛选、排序、增删改、进度快速更新、CSV |
| 岗位资料库 | 面试前集中复习 | 公司介绍、JD、要求、面试/笔试资料、问题和笔记 |
| 岗位发现 | 发现匹配机会 | 偏好、导入、去重、匹配度、行为记录和官网跳转 |
| AI 分析（二期） | 提高申请质量 | 原文与 AI 内容分区、差距、优先级、简历和面试建议 |

## 关键设计取舍

- **岗位与投递分离**：`jobs` 保存公司、岗位、JD 和来源；`job_applications` 只在真正投递后创建。旧 `applications` 表保留，首次读取时做非破坏性数据迁移。
- **先确认再入库**：截图、文字、链接和表格都先形成临时确认行。AI 或解析器不能直接改写正式记录。
- **草稿不阻塞**：缺少公司或岗位的资料可以存为草稿；明确读取失败的项目留在失败列表，其他行继续保存。
- **重复由用户决定**：来源+岗位 ID、规范化链接、公司+岗位+地点依次判断；用户选择跳过、补充已有信息或独立保留。
- **事实优先**：基础简历由用户确认；AI 只能基于其中事实调整顺序和表达。新数字会被服务端事实检查拦截。
- **生成与投递分开**：保存岗位简历版本不会自动改状态，也不会自动成为某次投递使用的版本。

## 数据结构

`jobs` 保存岗位与资料；`job_applications` 保存实际投递；`import_batches` 和 `import_items` 支持幂等、逐条结果与撤销；`base_resumes` 保存原文件和确认内容；`resume_versions` 保存目标岗位、基础版本、JD 快照、建议和定制草稿。旧表只用于兼容迁移。

`discovered_jobs` 单独保存候选岗位，`discovery_preferences` 保存本机求职偏好，`discovery_states` 保存收藏、查看、不感兴趣、官网跳转和确认投递状态。候选岗位只有在用户确认投递后才去重并进入 `jobs` 与 `job_applications`。

AI 结果始终与原始 JD、基础简历分开显示和保存，不覆盖用户资料。

## 开发步骤

1. 已完成：岗位与投递基础管理、资料库、搜索筛选、统计
2. 已完成：快速新增、文字/链接/截图/CSV/Excel 导入、确认、去重、撤销
3. 已完成：基础简历、单岗位分析、差异审核、版本保存、DOCX/PDF 导出
4. 已完成：岗位发现基础版、偏好、手动候选导入、筛选、收藏、行为记录、本地匹配、确认投递
5. 下一阶段：腾讯、字节跳动、四大及合规的公开公司来源适配器
6. 后续阶段：候选岗位 AI 证据分析、浏览器快捷收藏、相似岗位复用优化、批量简历生成
7. 公开部署前再做：登录、用户数据隔离、隐私审查

## 二期匹配分建议

先处理毕业时间、招聘类型、地点、截止状态等硬性条件。总分 100：岗位方向 30、技能关键词 25、经历和项目依据 25、教育专业 10、历史行为 5、发布时间 5。历史行为占比较小，推荐中保留相邻方向，避免范围越来越窄。每一项显示具体依据；AI 只负责生成事实证据清单，不自行编造匹配分。

## 风险与边界

- 不抓取要求登录、验证码或明确禁止自动访问的网站。
- 不把 API Key、简历正文和个人联系方式提交到公开仓库。
- 当前 MVP 是个人使用模式；公开部署并存放真实数据前必须添加身份验证。
- 自动识别和 AI 结果需要人工确认后才能写入核心字段。
